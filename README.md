# FlawScope · 多智能体工业设备故障诊断系统

![CI](https://github.com/ludi11117/FlawScope-/actions/workflows/ci.yml/badge.svg)

用自然语言描述设备故障，系统自动完成 **信息抽取 → 知识检索 → 故障诊断 → 方案审核 → 辩论仲裁 → 成本精算 → 工单生成** 的全流程，并支持多轮追问与图片输入。

---

## 一、核心特性

| 特性 | 说明 |
|---|---|
| 多 Agent 协作 | 诊断师、审核师、成本精算师、工单生成师各司其职，通过共享状态协作 |
| 辩论仲裁 | 审核不通过时自动辩论，最多 3 轮，用尽仍无共识则标记高风险 |
| 混合检索 RAG | BM25 关键词 + 向量语义，用 RRF 按排名融合，两路结果都不会被整段挤掉 |
| 诚实降级 | 知识库无依据 / 资料不相关时明确说"无法判断"，不编造根因 |
| 失败不空转 | 模型调用失败时立刻短路：不调用审核、不进辩论，直接产出带风险标记的工单 |
| 多轮追问 | 信息不足时主动反问，而非硬猜 |
| 多模态输入 | 支持上传报警截图 / 故障照片，视觉模型转文字后合并诊断 |
| 规则化成本 | 模型只提取备件与工时，价格由 Python 价格表精确计算；价格表未覆盖的备件显式提示待核价 |
| Schema 强校验 | 每个 Agent 输出必须符合字段类型约束，不合法直接拦截 |
| 历史可追溯 | 每次诊断落库 SQLite（前端与 API 均落库），可搜索、筛选、导出 |
| 可观测性 | 结构化日志 + correlation_id 全链路追踪；Token 用量取自服务端真实 usage，Token 与耗时均按节点归因 |
| 过程可演示 | 两个离线工具（`trace_diagnosis.py` / `explain_retrieval.py`）把状态机流转与检索三路排名摊开；状态机流转图有测试守着不腐烂 |
| 降级有出口 | 任何失败/降级都产出带风险标记的工单，用户永远拿得到可读结果，不会只看到一句报错 |
| 格式错可自修 | Schema 不合规会把校验报错回灌给模型要求修正，不把"格式小错"当成"模型服务异常" |

## 三、完整工作流程

整个流程靠一个共享字典 `AgentState` 协作——每个节点从它**读**输入、把结果**写**回去。

```
用户输入
   │
   ▼
[0] extract_info   提取结构化信息
     extract_fault_info() → {设备类型, 报警代码, 故障现象, 排除条件}
     ├─ 返回 None（模型不可用）──→ [6] cost（不追问用户，直接出降级工单）
     │
   ▼
[0.5] check_info   信息是否充分？
     is_info_sufficient()
      ├─ 不足 → generate_followup_question() → END（返回追问）
      └─ 充分 ─┐
              ▼
[1] retrieve       混合检索证据
     retrieve_evidence()  BM25 + 向量
   │
   ▼
[2] diagnose       诊断
     先查"无依据 / 不相关" → 诚实降级
     agent_diagnose() → diagnosis
     ├─ 降级 / 模型失败 ────────→ [6] cost（工单标"待人工确认"）
     ▼
[3] review         审核
     agent_review() → review
   │
   ├─ 通过 ──────────────────→ [6] cost
   ├─ 审核没产出（模型失败）──→ [6] cost（跳过辩论，不做无意义空转）
   ├─ 诊断已是降级形态 ───────→ [6'] human_review（不辩论，避免凭空编造根因）
   │
   ▼ 不通过
[4] rebuttal       辩论反驳（带驳回理由重新检索）
     agent_rebuttal() → rebuttal
   │
   ▼
[5] final_review   最终复审
     agent_review_final() → final_review
   │
   ├─ 通过 ──────────────────→ [6] cost
   ├─ 没审出结果 ────────────→ [6] cost
   ├─ 不通过且未达 3 轮 ──────→ 回到 [4]
   └─ 已达 3 轮 ─────────────→ [6] cost（工单标"高风险待复核"）
   │
   ▼
[6] cost           成本
     ├─ 已是失败/降级终态 → 跳过模型，直接给"待人工核算"占位
     └─ agent_cost() 提取备件/工时 → calculate_cost() 规则算钱
         └─ 提取失败 → 标 llm_failed（不静默当成功）
   │
   ▼
[6'] human_review  转人工
     标记 pending_human_review，随后同样走 [6] → [7]
   │
   ▼
[7] workorder      生成工单
     agent_workorder() → workorder
     （失败/降级时统一打风险标记，不再是"死胡同"）
   │
   ▼
  END
```

> **降级路径的唯一出口是"带风险标记的工单"。** 无论是知识库无依据、模型调用失败，
> 还是审核阶段判定结论不可采信，最终都会产出工单并在 `风险等级` 里写明原因——
> 用户永远拿得到可读的结果，而不是一句报错或一张空白单子。

### 四个关键协作机制

1. **信息不足 → 追问**
   `check_info_node` 用规则判断（有报警代码，或 设备类型 + 至少一个现象）。不足则生成追问，前端累积多轮输入后重跑全流程。

2. **诊断师 vs 审核师 → 辩论**
   审核不通过，诊断师带驳回理由**重新检索证据**反驳，审核师再复审。最多 3 轮（`max_debate_rounds`），用尽仍无共识则强制出结果并标记高风险——**有上限防死循环，有兜底防卡死**。

3. **模型 vs 规则 → 分工**
   理解语言的任务（抽取/诊断/审核）交给 LLM；需要精确的计算（成本）交给 Python 规则。模型只提取备件和工时，绝不让模型算数。

4. **失败即短路 → 不空转、不静默**
   任何一次 LLM 调用彻底失败（熔断 / 重试耗尽）或输出无法通过 Schema 校验时，节点会写入 `llm_failed` 状态：
   诊断失败 → 不调用审核、不进辩论，直接出带"待人工确认（模型服务异常）"标记的工单；
   审核失败 → 没有驳回理由可辩，跳过整段辩论。
   这样既省掉最多 2N 次无效调用，也避免用户拿到一张空白工单却不知道出了什么问题。

## 五、快速开始（本地）

### 1. 环境准备

```bash
# 创建虚拟环境
python -m venv venv

# 激活（Windows）
venv\Scripts\activate

# 安装依赖
pip install -r requirements.txt
```

### 2. 配置密钥

在项目根目录创建 `.env`：

```
SILICONFLOW_API_KEY=你的密钥
SILICONFLOW_BASE_URL=https://api.siliconflow.cn/v1
```

> 密钥申请：https://siliconflow.cn

### 3. 构建知识库（首次或知识库更新后）

```bash
python tools/validate_knowledge_base.py   # 先自查格式（强烈建议）
python build_knowledge_base.py            # 重建（默认先清空再写入，可重复执行）
python build_knowledge_base.py --dry-run  # 只看切分结果，不写库、不调模型
python build_knowledge_base.py --append   # 追加而不清空（一般不需要）
```

> 默认是**清空重建**：`Chroma.from_texts` 是追加语义，直接重跑会让库里的块数翻倍，
> 检索结果里全是近重复条目。重建是幂等的，跑 N 次结果一致。
> 改完知识库原文后需要**重启后端**，运行中的进程仍持有旧索引。
> 构建前会做**格式自检**，解析不出『可能原因』条目时会拒绝构建（加 `--force` 可强制）。

### 3.1 换成你自己的数据

**知识库是可替换的数据，不是写死的示例**——把 `data/knowledge_base.txt` 换成你们厂的
资料，系统就按你们的资料答。完整格式约定见 **[docs/数据接入契约.md](docs/数据接入契约.md)**。

接入三步：

```bash
# ① 写好自己的资料，替换 data/knowledge_base.txt（格式见契约文档）
# ② 自查：解析出多少条『可能原因』
python tools/validate_knowledge_base.py
# ③ 通过后构建
python build_knowledge_base.py
```

> ⚠️ **为什么必须自查**：如果系统解析不出『可能原因』条目，**排除条件映射会静默失效**
> ——系统照样出诊断，只是用户说的"已排除某某"不再被遵守，且**不报错**。
> 自查脚本会把这类问题在接入阶段就暴露出来。
>
> 换库后请同步跑 `pytest tests/test_eval_dataset.py -q`：它断言"黄金根因必须在
> 知识库里能找到依据"。它红了说明你在用库外的答案考系统，需要同步调整用例。

### 4. 启动

```bash
# 推荐：一键启动后端 + React 前端（Windows）
启动全部.bat
#   → 后端 http://127.0.0.1:8000/docs
#   → 前端 http://127.0.0.1:5173

# 或分别启动（各自开一个窗口，单独调试时用）
启动后端.bat                # uvicorn api:app  :8000
启动React前端.bat           # vite dev         :5173

# 或命令行直接测试诊断流程
python orchestrator.py
```

**启动过程说明**（`启动全部.bat` → `run_all.py`）：

- **只有一个窗口**。两个服务作为子进程跑在同一个控制台里，日志分别加
  `[后端]` / `[前端]` 前缀；Ctrl+C 一次停掉全部（含 npm 派生的 node 进程，
  不会留下占着 5173 端口的孤儿进程）。
  之前用 `start cmd /k` 会弹出三个黑窗口，且关哪个窗口都不算干净地停止。
- **浏览器不等后端**就打开——前端端口起来就跳页面。后端还在初始化时，
  顶栏状态灯显示"正在启动 3/5 加载向量库"，好了一键变绿。
  这样等待是**可见的**，不用对着黑窗口猜还要多久。
- 后端 import + 初始化约 **6~10 秒**（依赖 import 占大头）。启动器会实时显示进度。
  > ⚠️ 若本地装了 `torch`，会凭空多出约 3 秒——`langchain_core` 顶层无条件
  > `from transformers import ...`，而 transformers 检测到 torch 就把它 import 进来。
  > 本项目不用本地推理，详见 `requirements.txt` 顶部注释。启动器检测到会提示卸载。

> 旧的 Streamlit 前端（`streamlit run app.py`，:8501）已不再是日常入口——
> 诊断页 / 历史页 / 统计页都已迁移到 React。仅在需要对照旧实现时本地启动。
> **容器不再启动它**：`entrypoint.sh` 只起 FastAPI，`requirements-runtime.txt`
> 也已不含 `streamlit` / `pandas`。要用旧前端请用 `requirements.txt` 本地跑。

## 六、局域网访问（让同事/其他人用）

React 前端默认只监听本机。要让同网段他人访问，需让 Vite 绑定所有网卡：

1. 在 `web/` 下运行：`npm run dev -- --host 0.0.0.0`
2. 查询本机 IP：`ipconfig`（找到 IPv4 地址，如 `192.168.2.48`）
3. 同一 WiFi 下其他人访问：`http://192.168.2.48:5173`

**注意端口与代理**：前端把 `/api` 代理到 `127.0.0.1:8000`，所以后端也要同时
监听可被访问的地址（`uvicorn api:app --host 0.0.0.0 --port 8000`），否则页面
能打开但诊断请求会失败。

**首次可能被 Windows 防火墙拦截**，管理员 PowerShell 放行：

```powershell
New-NetFirewallRule -DisplayName "FlawScope 前端 5173" -Direction Inbound -LocalPort 5173 -Protocol TCP -Action Allow
New-NetFirewallRule -DisplayName "FlawScope 后端 8000" -Direction Inbound -LocalPort 8000 -Protocol TCP -Action Allow
```

**设计要点：**

- **镜像瘦身**：`requirements-runtime.txt` 去掉 torch / transformers（本项目用在线 API，不需要），
  也去掉只服务于旧前端的 `streamlit` / `pandas`，镜像体积大幅减小

- **密钥安全**：`.env` 已加入 `.dockerignore`，不进镜像，运行时通过 `env_file` 注入

## 八、API 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/diagnose` | 提交故障描述（可带图片）执行诊断。并发超过上限时返回 `503` + `Retry-After` |
| GET | `/records` | 查询诊断历史（支持 `keyword` / `status` / `limit` / `offset` 分页） |
| GET | `/records/{id}` | 单条记录详情 |
| GET | `/records/{id}/workorder.md` | 把该条记录的工单导出为可打印的 Markdown |
| DELETE | `/records/{id}` | 删除指定记录 |
| GET | `/stats` | 统计信息 |
| GET | `/health/live` | **存活探针**：只确认进程在，不触碰外部依赖，毫秒级返回 |
| GET | `/health/ready` | **就绪探针**：启动初始化是否完成、能否接诊断请求。未就绪返回 `503` + 进度 |
| GET | `/health` | **依赖健康**：探活 LLM / Embedding / ChromaDB / SQLite，结果默认缓存 60s（`?fresh=true` 强制真探） |

三个探针的分工是刻意区分的，混用会出问题：

| 端点 | 回答什么 | 启动初始化期间 |
|---|---|---|
| `/health/live` | 进程要不要被重启 | **200**（进程确实活着） |
| `/health/ready` | 请求现在能不能成功 | **503**（还没初始化完） |
| `/health` | 依赖（LLM/向量库…）全不全 | 依赖未加载 → unhealthy |

> ⚠️ **不要拿 `/health/live` 判断"能不能用"**。它在启动过程中就返回 200，
> 而此时向量库还没加载、诊断必然失败——前端状态灯早期只看 liveness，
> 于是冷启动那几秒显示"服务正常"，用户点下去拿到一个失败。
> 判断可用性请用 `/health/ready`。

> `/health` 会真实调用一次 LLM 与 Embedding。Docker healthcheck 每 30s 打一次，不做缓存会持续烧配额并拖慢探活；因此默认加了 TTL 缓存，容器编排的 livenessProbe 请改用 `/health/live`。

> `/health/ready` **只读内存状态**，不触碰任何依赖，可以放心高频轮询（前端默认 5s，启动中 1.5s）。

> **鉴权（可选）**：在 `.env` 里设置 `API_KEY` 后，上表所有业务接口（`/diagnose`、`/records*`、`/stats`）
> 都需带 `X-API-Key` 请求头；不设置则不校验（本地开发默认）。探针 `/health*` 与 `/` 始终开放。
> ⚠️ 它**保护不了前端**：React 静态站（nginx :8080）是另一个进程，公网部署要另行加反向代理认证。

> **输入上限**：`/records` 的 `limit` 上限 500、`offset` 必须 ≥ 0；`fault_description` 上限 4000 字符；
> `image_base64` 有长度上限（默认约 6MB 原图，见 `MAX_IMAGE_BASE64_CHARS`），超限直接返回 422。

> **并发闸门**：`/diagnose` 同时在跑的诊断数由 `MAX_CONCURRENT_DIAGNOSES`（默认 4）控制。
> 一次诊断要串行发起 6~9 次 LLM 调用、耗时数十秒，不设闸门时突发流量会占满 FastAPI 线程池
> （连 `/health` 都要排队），并把模型配额成倍烧掉。超限时**明确返回 503** 而不是无声排队——
> 排队只会让调用方挂到超时，还一直占着线程不放。

> **分页**：`/records` 的 `total` 是匹配总数（独立 `COUNT(*)`），不受 `limit` 影响；
> 翻页用 `offset`。响应里会回显 `offset` / `limit`，调用方不必自己记取了哪一段。

```bash
# 第二页（每页 20 条）
curl "http://localhost:8000/records?limit=20&offset=20"

# 导出 12 号记录的工单（Markdown）
curl -OJ "http://localhost:8000/records/12/workorder.md"
```

示例：

```bash
curl -X POST http://localhost:8000/diagnose \
  -H "Content-Type: application/json" \
  -d '{"fault_description": "设备类型：数控机床主轴电机\n报警代码：E-203\n现象：主轴转速不稳定，异响"}'
```

### 前端真渲染验证（`tsc` 绿 ≠ 界面正确）

所以改了**样式或状态渲染**之后，要跑一次真渲染脚本（playwright 装在隔离工作区，

| `verify_health_ui.mjs` | 顶栏状态灯 + 诊断页未就绪横幅。用**路由拦截**构造三种后端状态，确定可复现（靠真实后端抓不到"启动中"那 1 秒窗口） |
| `verify_stats_ui.mjs` | 统计页指标卡与状态条形。打**真实后端**，验的正是"真实数据 → 真实条形"这条链路 |

### 两个离线演示工具（不联网、不花钱）

这两个脚本解决的问题是：**读代码只能看到"应该怎么走"，跑一遍才能看到"实际怎么走"**。

#### `tools/trace_diagnosis.py` —— 状态机逐节点 trace

```bash
# 跑全部 6 个场景，逐节点打印输入/输出/耗时
venv/Scripts/python.exe tools/trace_diagnosis.py

# 只看辩论环（⑥⑦ 会走两遍）
venv/Scripts/python.exe tools/trace_diagnosis.py debate

# 导出机器可读 trace，可用于"改状态机后比对访问序列"
venv/Scripts/python.exe tools/trace_diagnosis.py --json
```

它跑的是**真实的** `orchestrator.app`（真 LangGraph），只把调模型处换成固定回答。
六个场景覆盖主干与全部四条提前退出岔路：

| 场景 | 看什么 |
|---|---|
| `happy` | 9 节点走满；成本由 Python 算出（850+80+2×150=1230），模型不参与算术 |
| `followup` | 信息不足 → 停在 ②追问，检索/诊断/成本全都没执行 |
| `no_knowledge` | 检索为空 → 诚实降级，**诊断师根本没被调用** |
| `guard` | 资料是别的设备（E-101 vs E-203）→ 确定性护栏拦下，不跨设备瞎猜 |
| `llm_down` | 抽取阶段就失败 → 短路，**不把服务故障甩锅给用户** |
| `debate` | 审核一直不通过 → ⑥⑦ 成环，标高风险出工单 |

> ⚠️ 脚本会明确标注：因为模型被打桩，**token 恒为 0、耗时只反映节点分发开销**，
> 不代表真实性能。真实数字要靠 `eval_test.py` 联网跑。这个免责声明是刻意保留的——
> 演示数据被误当成性能数据，是这个项目一贯要避免的那类"自我合理化"。

#### `tools/explain_retrieval.py` —— 混合检索可解释化

RAG 最容易被追问"检索怎么调的、为什么出来这几条"。只看最终 evidence 回答不了，
因为那已经把两路排名和融合过程抹掉了。这个脚本分三层打印：

```
■ 通道：BM25 关键词（取前 3 条 / 库中共 73 块）
     1. 三、主轴电机报警代码E-230 ...
■ 通道：向量语义（取前 3 条 / 库中共 73 块）
     1. 二、伺服电机定位漂移 ...
■ RRF 融合（rrf_k=60）
     排名   入选    BM25排   向量排     融合分       内容
     1    ✓     2       3       0.032002  二、主轴电机报警代码E-101 ...
     2    ✓     1       —       0.016393  三、主轴电机报警代码E-230 ...
     3    ✓     —       1       0.016393  二、伺服电机定位漂移 ...
```

每一条都能回答"**它凭什么入选**"：两路都命中的 `E-101` 得分 0.032 排第一；
只被 BM25 命中的 `E-230` 和只被向量命中的"伺服电机漂移"各得 0.016。
`--json` 可导出完整报告。

> ⚠️ 同样有免责声明：离线跑必须给查询嵌入打桩（否则要联网调 API），
> **排名会失真**——它演示的是**管道结构**（两路怎么各自排名、融合怎么定名额），
> 不是真实检索质量。要看真实排名，配好真 key 后去掉桩。

`docs/状态机流转图.md` 是 Mermaid 图 + 五条退出路径说明。

### 自动化评估

```bash
# 三类硬指标评估（对 test_cases.json 逐条评估，含 LLM 判官 + 程序化确定性指标）
python eval_test.py

# 免判官快速验证（只跑程序化指标，调试用）
python eval_test.py --skip-judge --limit 3

# 指定判官模型（建议用与诊断模型不同源的模型消除偏倚）
python eval_test.py --judge-model deepseek-ai/DeepSeek-V3
```

评估输出 8 项硬指标（报告写入 `eval_reports/`，含 JSON 与 Markdown）：

| 指标 | 类型 | 说明 |
|---|---|---|
| ① 终诊根因·核心一致率 | LLM 判官 | 命中至少一条黄金根因（宽松） |
| ② 终诊根因·全覆盖率 | LLM 判官 | 覆盖全部黄金根因（严格） |
| ③ 幻觉率 | 程序化 | 终诊原因是否全部接地于**本次检索命中的资料片段**（jieba 分词同句匹配） |
| ④ 排除条件遵守率 | 程序化 | 被排除关键词是否泄漏进终诊 |
| ⑤ 完整输出率 | 程序化 | 诊断/审核/成本/工单各节点是否全部产出有效结构 |
| ⑥ 诚实降级 | 程序化 | 知识库外对抗案例是否拒绝编造 |
| ⑦ 误降级 | 程序化 | 有依据案例是否错误拒绝诊断 |
| ⑧ 辩论增益 | 判官对比 | 初诊 vs 终诊 修正/恶化/持平 |

设计要点：判官默认用 `72B` 独立模型（与诊断用的 `14B` 不同源，消除同源偏倚）；幻觉率、排除条件、降级等指标全部程序化实现，零 LLM、可复现。

**幻觉率的溯源口径**：指标③比对的语料是 `retrieve_evidence()` 本次实际拼接出的 `【资料N】`
片段，**不是整份知识库原文**。原因是后者的判定过于宽松——只要那句话在库里的任何位置出现
就算"接地"，于是知识库越小、越容易碰巧命中，指标反而越漂亮（1.5 KB 的库下幻觉率恒为 0，
没有测量意义）。改为比对检索片段后，指标才真正回答"模型有没有引用它没检索到的内容"。
`tests/test_guards_and_pagination.py` 里有 4 条断言锁住这个口径，其中一条专门盯住
"评估流程是否把 evidence 传进了检测函数"——漏传会让指标静默退回宽松口径。

### 数据集规模与难度配比

`test_cases.json` 当前 33 例，刻意配了三类难度样本（`tests/test_eval_dataset.py` 断言其下限，
防止后续精简用例时把区分度删掉）：

| 类型 | 数量 | 作用 |
|---|---|---|
| 带排除条件 | 9 | 用户已实测排除某原因，考裁剪是否真的生效 |
| 无报警码（抗模糊） | 7 | 只给现象不给代码，考语义检索而非代码直查 |
| 诚实降级 | 3 | 库外设备/代码，必须拒绝编造 |

覆盖 15 种设备类型。难点用例包括：**近似故障码干扰**（E-203 vs E-230，同设备且都表现为
振动）、**跨设备同症状**（空压机 A-203 与主轴 E-230 都是剧烈振动，根因完全不同——这是
知识库只有 3 个主题时测不出来的）、**故障码撞车**（注塑机 E-203 与机床 E-203 代码相同、
设备不符，应降级而非套用机床根因）、**三重收窄**（E-203 三条根因排除两条，只剩轴承）。

知识库原文 `data/knowledge_base.txt` 现为 12 个设备类型 / **36 个故障条目** / 17 个故障码，
并**刻意保留了 36 处「经验分歧」**（署名老师傅对同一故障给出不同甚至矛盾的判断）；
在 `chunk_size=200` 下切分为约 **76 个向量块**；备件价格表 33 条。

> **为什么保留矛盾**：真实场景里老师傅的判断本来就常不一致。单 Agent 遇到"张师傅说 A、
> 李师傅说 B"只能二选一或和稀泥，**多 Agent 才有可能如实表达"这是两派意见"**。
> 冲突材料是多 Agent 辩论的存在理由，不是数据质量问题。详见 `docs/为什么必须多Agent.md`。
> 这些分歧现已接入审核清单第 5 项（`agents.extract_kb_disagreements()`）：审核师能看到
> 分歧，从而发现"诊断只取了一派"——此前这条线是断的，分歧躺在库里但没人看得见。

```bash
pytest tests/test_eval_dataset.py -q    # 校验黄金根因在库里都有依据
```

### 消融实验：凭什么说多 Agent 更好？

这是面试官一定会追问、也最容易答砸的问题。`ablate_single_vs_multi.py` 的设计要点：

| 要点 | 做法 |
|---|---|
| 单 Agent 基线 | `抽取 → 检索 → 一次诊断`，**无审核、无辩论、无 schema 回灌** |
| 可比性前提 | 两侧**共用同一次检索的 evidence**，且用 `eval_test` 的**同一套**判定函数 |
| 失败处理 | 单 Agent 调用失败**计为失败**，不从分母剔除（否则人为抬高其成绩） |
| 输出 | 6 项指标对照 + 逐用例明细，落盘 `eval_reports/ablation_<时间戳>.{md,json}` |

指标：核心一致率 / 全覆盖率 / 幻觉率 / 排除遵守率 / 诚实降级率 / 误降级率。

**已跑三轮，结论有胜有负**（2026-09-25 最新一轮：33 例，两侧 0 调用失败；
完整数据见 `eval_reports/` 与 `docs/消融实验-单Agent对多Agent.md`）：

| 指标 | 单 Agent | 多 Agent | 多 Agent 历史变化 |
|---|---|---|---|
| 核心一致率 | 30/30 = 100% | 27/27 = 100% | 持平（饱和，无区分度） |
| 全覆盖率 | 27/30 = 90.0% | 25/27 = 92.6% | 91% → 87% → 92.6% |
| 幻觉率 | 1/30 = 3.3% | 0/27 = 0% | 26% → 0%（已修复） |
| 排除遵守率 | 2/10 = 20% | 9/10 = 90% | 89% → 100% → 90% |
| 诚实降级率 | 0/3 = 0% | 3/3 = 100% | 持平（架构性优势） |
| 误降级率 | 0/30 = 0% | 3/30 = 10% | 15% → 10% |

⚠️ **上表的「全覆盖率」不能单独看，它的分母会被弃权缩掉。** 判官指标的分母是
「判官实际判过的用例」（`len(judged)`），而降级样本没有根因可判、`judgment` 为
`None`，被整个剔出分母——**每弃权一例，分母就少一**。多 Agent 比单 Agent 更容易
降级，所以这个口径**系统性地偏袒多 Agent**。把弃权留在分母里（严格口径）：

| 口径 | 单 Agent | 多 Agent | 差值 |
|---|---|---|---|
| 默认（弃权剔出分母） | 27/30 = 90.0% | 25/27 = 92.6% | +2.6pp（多 Agent 优） |
| **严格（弃权留在分母）** | 27/30 = 90.0% | 25/30 = 83.3% | **-6.7pp（多 Agent 劣）** |

**同一份数据，两种口径给出相反的结论。** 多 Agent 通过的**绝对例数本来就少**
（25 < 27），只是弃权把分母缩掉了——「没测到」不能冒充「测得好」。
两个口径现在都会出现在报告里（`②` 与 `②b`）。

一句话：**多 Agent 擅长拒绝（该拒绝时敢拒绝），不擅长收敛。**

> **三种结果都要照实写**：多 Agent 更优 → 给数字并说明增益集中在哪类用例；
> 无差异 → 说明这套题以"答案唯一"的直查题为主，增益应看分层统计；
> **多 Agent 更差 → 这是最有价值的发现**。**藏起不利结果比拿不出结果更糟。**

⚠️ **三个必须一起报的数**：

1. **辩论触发率只有 30–33%**（2026-09-25 实测 11/33；更早两轮是 73% → 30%）。
   多 Agent 幻觉率 26% → 0% 的同时触发率也在掉，"越界机会被抽走了"与"约束真的
   生效了"现有数据**区分不了**，不能把幻觉归零直接归功于提示词修复。
   触发条件目前唯一：审核师判"不通过"。库里刻意保留的 36 处「经验分歧」现已
   接入审核清单第 5 项，但**它能把触发率抬到多少，尚未实测**。
2. **全覆盖率的改善里有多少来自"分母缩了"**：默认口径 87% → 92.6% 看着是改善，
   但同期弃权数与分母都变了（见上表），单次运行区分不了。
3. **单次运行的数字不可引用**：同一份代码、同一批用例重跑，多 Agent 的"是否降级"
   在 30 个共同用例里**翻转了 5 例**（单 Agent 0 例）。所以
   `ablate_single_vs_multi.py --repeat N` 会给出跨轮摆动幅度——摆动大于差值时，
   那个差值就不能当结论。

机制层面的完整论证（单 Agent 为什么"结构上"缺少反对者、驳回理由如何被当作检索
query 使用、经验冲突材料为何使单 Agent 必然失真）见 `docs/为什么必须多Agent.md`。

## 十、关键设计决策（面试要点）

1. **为什么用状态机而不是线性代码？**
   因为需要条件路由、循环（辩论）、提前终止（追问），且每步状态可追溯。

2. **为什么要多 Agent 辩论？**
   单次诊断容易过度自信 / 幻觉，用独立的审核角色制衡，并通过辩论让诊断师基于新证据自我纠偏。
   **更本质的理由**：单 Agent 是"自己批自己的卷"，存在沉没成本与视角同源两个结构性缺陷，
   换更大的模型只会让它更自信地在错误前提上推理。多 Agent 的价值在于**结构性制造对抗**：
   审核师拿不到诊断师的推理过程（只能看结论），且**驳回理由会被当作检索关键词重新取证**
   （`orchestrator.py:242-246`），所以辩论不是两个模型互相说服，而是针对争议点补证据。
   详见 `docs/为什么必须多Agent.md`。

3. **为什么成本不让模型算？**
   模型算术不可靠。模型只做它擅长的"提取备件和工时"，价格用确定的业务规则计算。

4. **为什么用混合检索，以及为什么用 RRF 融合？**
   BM25 擅长精确关键词（报警代码、型号），向量擅长语义（"一顿一顿"≈转速不稳），两者互补。
   融合方式用 **RRF（Reciprocal Rank Fusion）** 而不是简单拼接：BM25 分与余弦相似度量纲完全不同，
   直接按分数排序会让其中一路垄断结果。RRF 只看排名（`score = Σ 1/(60+rank)`），
   两路各自的头部文档都能进最终结果，也天然完成去重。

5. **如何防止幻觉？**
   三重防护：检索无结果时降级、`check_relevance` 相关性核验、提示词强约束"不得添加资料外原因"。

6. **怎么证明"不是纸面设计"？**
   两个离线工具把内部过程摊开：`trace_diagnosis.py` 跑真实 LangGraph、逐节点打印
   输入/输出/耗时与状态变迁；`explain_retrieval.py` 打印向量/BM25/RRF 三路排名与逐条融合分。
   两者都**主动标注免责声明**（打桩后 token 恒为 0、排名失真），不用演示数据冒充真实指标。
   状态机流转图由 `tests/test_state_diagram.py` 守着不腐烂。

7. **为什么评估指标会"下降"反而是好事？**
   扩库前所有指标满分（100% / 0% / 100%），但那是**测量失效**：知识库只有 8 块、
   `RETRIEVAL_K=3` 覆盖 37%，检索不可能失败；8 条用例 7 条带直接故障码，模型想编都难。
   扩充到 44 块 / 30 用例后指标反而下降（全覆盖 87.5%、排除遵守 66.7%）——
   **下降说明指标开始有区分度了**，也才第一次暴露了两个真实缺陷。
   详见 `docs/缺陷复盘.md`。

8. **审核师"有牙"是辩论能触发的前提（一个真实缺陷）**
   曾经的 `agent_review.j2` 只有一句"请审核是否合理"，还带一条枷锁：
   "必须严格基于【诊断结论】审核，不得假设或要求额外的资料内容"。
   后果是**审核师没有对照物**——它只能看诊断结论是否自圆其说，而诊断提示词又
   强制模型写满知识库里的全部原因（"即使认为可能性较低也必须列入"）。
   **一个没有对照标准的审核者，面对一个被强制写满的诊断，只能通过。**
   于是辩论极少触发，多 Agent 实际退化成"单 Agent + 一次无害审核"。

   修法不是删掉枷锁（那条本意是防审核师自己编造），而是**给它合法的对照物**：
   把 `{{evidence}}` 和 `{{fault}}` 一起传给审核师，并给出四项可据以驳回的检查
   （越界 / 遗漏 / 排除 / 依据强度），同时**明令禁止超范围质疑**。
   这样既保住了防幻觉防线，审核也真正有了牙。

   > 这个缺陷说明一件事：**节点分离只是"结构上"有了对抗，提示词强度不对等会让对抗空转。**
   > 看架构图看不出这个问题，只有读提示词 + 看流程走向才能发现。

## 十一、已知限制与改进方向

### 已解决

- **失败不静默**：信息抽取失败不再伪装成"信息不足"去追问用户；成本计算失败不再报成功
- **降级路径统一**：知识库无依据 / 模型失败 / 审核判定不可采信，三条路径都产出带风险标记的工单，不再有"死胡同"
- **口径一致**：辩论翻盘后，工单里的根因与审核意见同源（都取最终结论），不再自相矛盾
- **Schema 小错可自修**：字段类型/缺失不再等同"模型服务异常"，会先回灌报错让模型修正一次
- **熔断器语义**：成功即清零失败计数（真正是"连续失败"），并加锁保证多线程下状态一致
- **报警代码比对**：`E-203` / `E203` / `e 203` 视为同一代码，消除由此产生的误降级
- **设备类型比对容忍同义不同名**：用户说"空气压缩机"、知识库标题写"空压机"时不再误判无依据
- **审核提示词强度失衡**：审核师此前拿不到检索资料，等于无对照物，导致辩论空转
  （详见「关键设计决策」第 8 条）
  此前是裸的精确子串比对，`"空气压缩机" in evidence` 为 False 就把一个本来能答的案例降级掉了。
  这个缺陷在知识库只有 3 个主题时**完全暴露不出来**——那时"空压机"只作为对抗案例出现，
  误降级与正确的降级长得一模一样。扩库后它才浮出水面。现走同义词表 + 头部名词降级两道路径，
  且配了对偶测试（既测"同义要放行"，也测"真不匹配要拦下"），防止护栏被越改越松
- **辩论不得静默丢掉候选根因**：初诊提示词硬性要求"有几项写几项、不得自行取舍"，
  但辩论提示词没有等价约束、且辩论会换查询重新检索，于是辩论阶段可以把候选收敛掉——
  表现为**核心一致率满分、全覆盖率掉分**（每个 Agent 单独看都没错，是链路上的**约束漂移**）。
  现由 `agents.restore_dropped_candidates()` 做确定性兜底：初诊里"有依据、未被用户排除、
  与终诊条目也不语义重复"的原因会被补回终诊，而不是再加一句提示词
- **护栏绝不改写降级结论**：上述护栏的第一版有个真实事故——降级判定写在"拆分候选"之后，
  而降级文案 `知识库无相关依据，无法诊断` 含全角逗号，拆完被切碎，逐片判断全部落空，
  结果把每张降级工单都改写成"无相关依据; 无法诊断; <编造的根因>"，直接打穿诚实降级防线。
  现判定提前到拆分之前，并统一 `_DEGRADED_MARKERS` 口径
- **降级标记不会两处漂移**：`agents` 因循环依赖不能直接 import `orchestrator` 的标记表，
  手工副本有静默漂移风险；现由 `_assert_degraded_markers_in_sync()` 在首次使用时校验并断言
- **相关性判定**：模型输出无法解读时返回"未验成"，不再默认当作"相关"放行
- **鉴权与输入上限**：API 支持可选 `API_KEY`；图片 base64 与 `limit` 均有上限
- **统计性能**：Token 汇总改为冗余列 `SUM()`，不再每次全表解析 JSON
- **分页语义**：`/records` 的 `total` 改为独立的 `COUNT(*)`，不再是被 `LIMIT` 截断后的行数
  （此前 `limit=10` 时 `total` 恒为 10，调用方无法判断"还有没有更多"）
- **评估口径**：`evaluate_semantic` 要求模型明确回答"一致"；含糊措辞（如"不确定是否一致"）
  不再因为不含连续子串"不一致"而被算作命中
- **并发安全**：BM25 索引构建加锁 + 双重检查（此前并发首次检索会把整库分词重复做 N 遍）；
  LLM / Embedding / ChromaDB 四个懒加载单例同样加了可重入锁——裸的 `if _x is None` 在
  Streamlit 多会话 + FastAPI 线程池下会把同一个客户端构造多次，Chroma 重复打开同一
  persist 目录还会争抢底层 SQLite 锁
- **统计快照隔离**：`TokenTracker.get_summary()` 改为深一层拷贝，后续 LLM 调用不再改写已产出的快照
- **归因不串味**：工单生成失败时若本轮本就是降级终态，保留原状态（"知识库无依据"不会被改写成"模型服务异常"）
- **可追溯**：诊断历史新增 `correlation_id` 列（自动迁移），记录可直接对回那一轮的结构化日志
- **可观测性**：Token 之外增加按节点耗时归因；Streamlit 侧也走统一日志配置
- **前端计数不再失真**：历史页的"共找到 N 条记录"改用 `count_records()`，不再是 `len(records)`
  （此前被 `LIMIT` 截断：库里有 500 条也只显示 20 条，用户根本不知道还有更多）
- **分页闭环**：`get_records` / `/records` 补上 `offset`，前端历史页加了翻页控件与页码越界夹取。
  此前只修了 `total`，调用方知道"还有更多"却取不出第二页，等于只修了一半
- **知识库构建幂等**：`build_knowledge_base.py` 改为默认「先清空再写入」并支持 `--dry-run`。
  `Chroma.from_texts` 是**追加**语义，此前每次重跑都会让库里的块数翻倍（近重复条目会刷屏检索结果、
  白烧 context，并让 RRF 融合被同源文档占掉多个名额）。同时路径统一取 `settings`，
  不再写死 `chroma_db` 而绕过 `CHROMA_PERSIST_DIR`
- **诊断过载保护**：`/diagnose` 加并发闸门（`MAX_CONCURRENT_DIAGNOSES`），超限明确 503 + `Retry-After`
- **工单可直接打印**：新增 `/records/{id}/workorder.md` 与前端"导出工单 Markdown"按钮。
  降级工单只渲染它真正有的字段，不补空的"维修方案"章节
- **配置现代化**：`config.py` 从已废弃的 `class Config` 改为 `SettingsConfigDict`（Pydantic v2 起弃用，v3 将移除）
- **CI**：新增 ruff 静态检查；原型脚本归档到 `legacy/`
- **容器入口不再指向已弃用的前端**：`entrypoint.sh` 此前仍在 `streamlit run app.py`（:8501），
  而 README 已写着「旧前端不是日常入口」——文档与部署形态对不上，容器起来跑的是没人维护的界面。
  现入口只起 FastAPI（并用 `exec` 让 uvicorn 直接成为 PID 1，信号处理比原来的 `trap` + `wait` 更可靠），
  `Dockerfile` 改 `EXPOSE 8000`，compose 移除 8501 映射。
  顺着清掉两处死重量：`requirements-runtime.txt` 不再装 `streamlit` / `pandas`
  （正式代码里只有 `app.py` 用它们）；`config.py` 的 `STREAMLIT_PORT` / `STREAMLIT_ADDRESS`
  是只定义、从未被读取的死配置。
  另修掉一处真 bug：`启动公网隧道.bat` 此前把隧道指向 8501，**等于把已弃用的前端暴露到公网**；
  现改为指向 React 前端 5173（Vite 会把 `/api` 代理到 8000，隧道过去端到端可用），
  并按项目约定重写为纯 ASCII + CRLF

  `data/knowledge_base.txt` 的文件头「来源说明」里对读者明示，不做过度宣称。
  **为什么保留矛盾**：真实场景里老师傅的判断本来就常不一致；单 Agent 遇到"张师傅说 A、
  李师傅说 B"只能二选一或和稀泥，**多 Agent 才有可能如实表达"这是两派意见"**。
  冲突材料是多 Agent 辩论的**存在理由**，不是数据质量问题（详见 `docs/为什么必须多Agent.md`）。
  条目结构（`一、` 章节 / `1.` 编号原因 / `故障现象：` 前缀）是解析契约，
  与 `agents.extract_kb_causes()` 绑定，改写时不得破坏。

  **已实际调研过真实来源**（见 `docs/真实数据来源.md`）：公开渠道**不存在**真实维修工单数据集
  （真实工单是企业内部资产；网上标 "work order dataset" 的基本都是合成的）；
  找到了**西门子官方诊断手册**（订货号 `6FC5298-7AA20-3RP3`，822 页，`tools/parse_manual_pdf.py`
  可抽出 1170 条报警条目），但**内容与场景错位**——它是 CNC 系统的软件/通讯报警，
  与"机械故障诊断"真正相关的只有 `300xxx`/`400xxx` 约 264 条，
  且代码体系（6 位数字）与设备范围（仅 Siemens 840D）都与现有库冲突。
  **全量替换会净损失**：真实度上去，设备覆盖从 12 类掉到 1 类。
  故建议**双轨**（合成场景层 + 手册权威层），而非替换。
  ⚠️ 手册受版权保护，`data/raw/` 已 gitignore，**不得入库**。
  继续补权威来源仍是最有价值的一步；用 LLM 批量生成"像手册"的假数据则只有数字收益、无信息增益
- **检索溯源粒度**：幻觉检测现已比对检索命中的 chunk，但 chunk 边界来自固定长度切分，
  尚未按"故障条目"对齐；条目级切分能让溯源更准（也不会把相邻条目的原因算作命中）
- **BM25 索引**：已做进程内缓存（仅首次构建），但多进程/多副本下各自持有一份内存索引；知识库上万条后可换倒排索引或独立检索服务
- **用例集规模**：33 例仍偏小，判官指标（①核心一致率 / ②全覆盖率）的分母只有个位数
  （诚实降级率的分母**只有 3**），置信区间宽。继续补充**带标注的真实现场工单**比继续合成
  用例更有价值
- **辩论触发率只有 30–33%，接入分歧检查后尚未实测**：2026-09-25 已把库里 36 处「经验分歧」
  接进审核清单第 5 项（`agents.extract_kb_disagreements()`），但"它能把这个触发率抬到多少"
  需要再跑一次全量判官评估才知道——**这是当前最值得花的一次额度**，因为辩论不触发时，
  多 Agent 实际退化成"单 Agent + 一次审核"
- **降级判定不可复现**：同一份代码重跑，多 Agent 的"是否降级"在 30 个共同用例里**翻转 5 例**
  （单 Agent 0 例）。机制上：护栏 `is_equipment_in_evidence` 本身是纯函数，但它的输入
  `fault_info` 来自 LLM 抽取，上游抖动会传导到确定性的护栏上。两条修法——让抽取更稳
  （结构化输出 / 温度 0 / 多次投票取一致），或把降级判据从抽取结果上解耦
- **辩论候选保全护栏待真实评估验证**：离线回归已通过（含退化验证），
  但尚未在真实判官评估里看它把"全覆盖率"抬回来多少——这需要再花一次 API 额度跑全量 33 例
- **辩论与初诊的候选清单未强制同源**：当前靠护栏在**出口**兜底，属于后置补救。
  更彻底的做法是让辩论复用初诊的候选清单（或把清单显式传进 prompt），
  避免"重检索后候选集合变了"这层隐含假设
- **设备同义词表**：`agents.EQUIPMENT_SYNONYMS` 目前是手工维护的 11 组映射，
  覆盖面有限；长期应改为可配置项或从知识库标题自动抽取
- **排除条件粒度**：知识库条目把多种原因绑定为一条时，无法精细排除，需细化条目
- **结构化输出**：目前靠"提示词要求 JSON + 兜底解析 + 修复重试"。改用原生结构化输出（JSON mode / function calling）可进一步降低解析失败率与重试次数
- **链路追踪**：已有 correlation_id 日志、Token 与耗时归因，以及离线 trace 导出；
  仍可接入 LangSmith / OpenTelemetry 记录每步 prompt 与原始响应
- **真实检索排名未固化进评估**：`explain_retrieval.py` 因为要离线跑，给查询嵌入打了桩，
  排名失真。可考虑加"配真 key 时去掉桩"的分支，把真实三路排名也纳入回归对比
- **反馈闭环**：人工审核结论可回流知识库，形成越用越准的飞轮
- **并发与流式**：React 前端走 `/diagnose/stream`（SSE，节点级进度）；`/diagnose` 同步端点仍是阻塞调用，
  主要留给外部系统，长任务可改为任务队列 + 轮询
- **限流**：已有全局并发闸门（`MAX_CONCURRENT_DIAGNOSES`）与可选鉴权，但**没有按 IP / 租户的限流**，
  公网部署仍建议加 slowapi 或网关限流；闸门是全局的，一个调用方打满后其他人也会被 503
- **深翻页**：`offset` 分页在记录量很大时仍有 `OFFSET` 扫描成本（SQLite 要跳过前 N 行）。
  历史表到十万级后可换成游标分页（`WHERE id < ?` keyset pagination）
- **工单导出格式**：目前只导出 Markdown。现场若需打印归档，可再加 PDF / Word 渲染
- **前端会话**：多轮追问的上下文只存在前端内存中，刷新页面即丢失，可持久化到 SQLite
- **诊断中断**：React 前端已支持中断（abort 触发后端生成器 close，不会跑完剩余节点）；
  `/diagnose` 同步端点仍不可中断
- **前端历史页性能**：React 版已从"逐条渲染 JSON"改为紧凑表格 + 按需展开详情；
  Streamlit 旧版仍保留原实现
- **知识库健康检查**：启动时若 `chroma_db/` 为空只会在首次检索时告警，可在启动阶段就显式提示"请先执行 build_knowledge_base.py"
- **依赖锁定**：`requirements.txt` 只固定直接依赖，传递依赖未锁；建议用 `uv lock` / `pip-compile` 生成带 hash 的锁文件
- **前端鉴权**：`API_KEY` 只保护 API；React 前端自身无鉴权，公网部署需反向代理认证
