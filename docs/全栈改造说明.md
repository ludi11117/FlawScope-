# 全栈改造说明（React + FastAPI 前后端分离）

> 记于 2026-09-18。本次改动把前端从"Streamlit 直连业务模块"改为真正的前后端分离，
> 并顺带修掉了一个与本次改动直接相关的 P1 缺陷。

## 一、为什么改：原来的架构有个说不通的地方

改造前的真实数据流：

```
Streamlit app.py ──import──> orchestrator / agents
       │
       └── (x)  api.py 那 344 行从未被前端用过
```

`app.py` 直接 `import orchestrator.run_diagnosis`，**绕过了 `api.py`**。
接口层是给外部调用者准备的，但自己的前端没走。这在架构上不成立：
要么承认没有接口层，要么让前端走它。

这个叙事值得在面试里讲：**不是"嫌 Streamlit 不好看所以换 React"，
而是"我审计了自己的架构，发现前端旁路了接口层，把它补齐了"。**
前者是审美偏好，后者是工程判断。

改造后：

```
React (5173/8080) ──HTTP/SSE──> FastAPI ──> orchestrator / agents
                                     ↑
                              唯一入口，可独立测试与部署
```

## 二、新增的技术点（每条都能被追问）

### 1. SSE 流式推送（`POST /diagnose/stream`）

一次诊断要串行走 6~9 次 LLM 调用、耗时数十秒。改造前只能等全部跑完才返回，
用户在几十秒里看不到任何进展。

现在复用 `orchestrator.run_diagnosis_stream()` 生成器（**不重复业务逻辑**），
每个节点推一条 `progress` 事件，最后推 `result` + `done`。

**三个容易踩的坑，都已处理并写了测试：**

| 坑 | 后果 | 处理 |
|---|---|---|
| 不共用并发闸门 | SSE 成为绕开限流的后门，配额被打爆 | 共用同一把 `BoundedSemaphore` |
| 闸门在端点内 finally 释放 | 端点 early return 时诊断还没开始跑，闸门泄漏 | 在**生成器**的 finally 里释放 |
| 不关反代缓冲 | 逐节点进度退化成"最后一次性全出来"，SSE 白做 | `X-Accel-Buffering: no` + nginx `proxy_buffering off` |

### 2. 前端手写 SSE 解析（不用 EventSource）

`EventSource` 有三个致命限制：

1. **只支持 GET** —— 端点是 POST（故障描述可能很长，还带 base64 图片，
   塞进 URL 不现实且会撞代理的 URL 长度限制）；
2. **无法自定义请求头** —— 带不了 `X-API-Key`，后端开鉴权就用不了；
3. **断线自动重连** —— 对"重连就重跑一遍、每次烧 6~9 次 LLM 调用"的场景，
   自动重连是**有害的**。

所以用 `fetch` + `ReadableStream` 手写。最容易踩的坑：
**一个 SSE 消息可能被 TCP 切成多个 chunk，一个 chunk 里也可能含多条消息**，
必须在循环外累积 buffer、以空行分隔，不能按 chunk 直接解析。

### 3. 类型契约手写对齐

`web/src/types/contracts.ts` 里每个类型都标注了「契约来源：agents.py :: XXXOutput」。
不用 `openapi-typescript` 自动生成，原因是后端用中文键名（`根因判断` / `工单编号`），
自动生成会把键名原样搬过来但**丢掉语义**——看不出哪个字段是"降级时可能整体缺失"的。

### 4. 状态机 + 辩论环可视化

`StateMachineView.tsx` 把 9 个节点画成一条进度链。
改造前只有一行行滚动的文字日志，看不出"走到哪了、还剩几步、辩论环走了没有"。

辩论环（审核 ⇄ 反驳 ⇄ 复审）单独高亮——它是多 Agent 架构的核心，
也是"单 Agent 做不到"的论据所在。

### 5. 图表执行兜底（顺带修的 P1）

**问题本质是"兜底放错了层级"**：`workorder_node` 内部那段"工单生成失败"兜底，
只覆盖"走到了 workorder 但 LLM 挂了"。异常若发生在更早的节点（retrieve / diagnose /
rebuttal），图**到不了** workorder，异常直接冒到 `run_diagnosis` 的 `except` 被 raise 出去。

后果：用户烧掉几十次 LLM 调用、等了十几分钟，最终拿到 **0 交付物**——
而项目对外宣称的核心保证是"任何失败都产出带风险标记的工单，没有死胡同"。

修复：把兜底挪到最外层调用点（`build_abort_workorder()` / `build_abort_result()`）。

- `run_diagnosis`：except 分支改为 **return** 降级结果
- `run_diagnosis_stream`：except 分支改为 **yield** 降级终态 ——
  前端才能以"降级完成 + 待人工处理工单"收场，而不是"连接断开"
- 兜底工单**只含三项**（工单编号 / 风险等级 / 风险说明），
  不补空章节——没有依据的"维修方案"比没有更危险

**为什么这件事必须排在 SSE 之前做**：SSE 会把每个节点状态实时推给前端，
如果图在中间挂了而兜底没补上，前端会永远卡在"正在辩论"上，观感比原先更差。

### 6. recursion_limit 显式收口

此前全项目零配置，用 LangGraph 默认值 **10007**——最坏情况能执行上万次节点、
成倍烧掉配额才报错。新增 `GRAPH_RECURSION_LIMIT`（默认 100），
`invoke` / `stream` 均显式传入。

## 四、新增的 SSE 契约的一个细节

`result` 事件额外带 `record_id` 字段（`api.py` 在落库后回填）。
前端据此直接拼出工单下载地址 `/records/{id}/workorder.md`，
不必让用户跑到历史页去翻自己刚做完的这一次。

为此 `database.save_diagnosis_record()` 改为返回 `lastrowid`
（必须在同一个连接作用域内取，出了 `with` 块游标就失效了）。

```bash

```

> 的迁移已完成，Streamlit 版本不再是日常入口；如需临时启用，
> 本地跑 `python run_app.py`（用 `requirements.txt`，它含 streamlit）。

**两种环境下请求路径完全一致，不需要判断环境。**

## 七、历史页迁移（第二轮）

第一轮只切了诊断页，历史页留在 Streamlit。第二轮补上，因为"只做一半"在
面试里是个会被追问的点：为什么诊断页能走接口、历史页不能？

`web/src/pages/historyUtils.ts` 把可测的纯逻辑抽出来（分页夹取、状态配色、
CSV 序列化、时间格式化），组件只负责渲染。这样这些逻辑能被 vitest 直接覆盖——
**第一轮把 SSE 解析抽成 `api/sse.ts` 也是同一个理由。**

相比 Streamlit 版的两处实质改进：

1. **表格 + 按需展开**。原版每展开一条就渲染若干个 `st.json` 块，
   记录一多整个页面卡住；改成紧凑表格，点开才渲染详情。
2. **CSV 注入防护 + UTF-8 BOM**。模型输出不可信，以 `=` `+` `-` `@` 开头的内容
   加单引号前缀（否则 Excel 会当公式执行）；BOM 保证 Excel 正确识别中文。
3. **顺手修掉一处改名遗留**：CSV 导出前缀是 `agentdiag_records_*.csv`，
   项目早已改名 FlawScope，这里没跟上。改成 `flawscope_records_*.csv`。

### 迁移中测试抓到的一个真实缺陷

`pageWindow()` 的 `clamped` 信号一直失效：

```ts
// 错的
const requested = Math.max(1, Math.floor(page))   // 下界已被提前抹平
const clampedPage = Math.min(requested, count)
clamped: clampedPage !== requested                 // 永远为 false
```

`Math.max(1, ...)` 把下界夹取**提前做掉了**，之后再比就永远相等。
结果是前端失去了"你请求的页码其实不存在，我帮你修正了"这个信号
（调 `/records` 时 `offset` 会被静默改掉却不提示）。

修复是先原样记录调用方请求的页码，再做夹取：

```ts
const rawPage = Math.floor(page)
const requested = Number.isFinite(rawPage) ? rawPage : 1
const clampedPage = Math.min(Math.max(1, requested), count)
clamped: clampedPage !== requested
```

**这个 bug 是单元测试抓到的，不是靠人肉 review。** 它正好说明第九节里
"纯函数抽出来 + 补测试"这个决定是有产出的，而不是为了凑测试数量。

## 八、版本号的单点收口（顺手修的第二个缺陷）

全栈改造时把 FastAPI 的 `version` 从 `1.2.0` 提到 `1.3.0`，
但 `/health`、`/health/live`、`/` 三处**各自硬编码了 `"1.2.0"`**，全都没报错。

这是典型的"改了却没改全"，而且**它的隐蔽性特别高**：部署脚本的探活只看
HTTP 200，不会去比对版本号——所以线上会长期有一个"自称 1.2.0 的 1.3.0"。

修复：`api.py` 顶部定义 `API_VERSION` 作为唯一来源，四处引用它。
并加了两条测试守着：一条扫源码确保只有一个版本号字面量，
一条检查四个出口返回的版本号互相一致。

**这条测试的退化验证第②步救过一次**：只把 `API_VERSION` 常量改了、
漏改 `HealthResponse` 的默认值，测试能立刻报红——
这验证了它真的在守"改漏一处"这个场景，而不是只在"完全没改"时才响。

## 十、一个被证伪的怀疑（值得记下来）

改造过程中跑测试，`tests/test_data_contract.py` 有两项报
「知识库解析 276 条（基线 104）」。我第一反应是"测试间状态污染"，
但复查后**这个判断是错的**：

`data/knowledge_base.txt` 的 mtime 是 **15:53:21**，而我那批测试跑在 **15:56**。
也就是说**知识库文件在那一刻真的被改写过**（同一时间窗内有另一个会话在活跃），
之后又被改回 104 条，所以我后来复跑就正常了。

**测试是对的，而且它做了它该做的事**：
`test_existing_knowledge_base_parses_stably` 的存在意义就是守住"知识库基线漂移"，
它准确地拦下了一次未被预期的数据变更。

这条记下来的价值有两点：
1. **"测试失败"未必是测试的问题**——先看数据源有没有被人动过；
2. 反过来也成立：**如果当时图省事把基线从 104 改成 276 让它变绿，
   就正好把这道防线拆了**。所幸没那样做。

## 十一、面试可讲的三句话

1. **架构自查**：我发现自己的前端绕过了接口层，`api.py` 形同虚设——把它补齐了。
2. **流式的三个坑**：共用闸门（否则成后门）、生成器内释放（否则泄漏）、
   关缓冲（否则退化成非流式）——每个都有测试守着。
3. **先修兜底再上流式**：因为流式会把"图挂了不给交付物"这个缺陷
   从"少交付"放大成"连接挂死"，所以顺序不能反。

再补一句关于测试的：**别急着让失败的测试变绿**。本轮有两次"测试红了"的价值
远大于"测试绿了"——一次是它抓出 `pageWindow` 的 `clamped` 恒假（真 bug），
一次是它拦住了一次未预期的知识库变更（数据被动过）。
如果当时把基线改掉让它变绿，两道防线就都没了。

## 十二、统计页迁移（第三轮）

第三轮把最后一个留在 Streamlit 的页面（系统统计）也切了过来，
至此 `app.py` 只剩"对照旧实现"的价值。

### 与 Streamlit 版的实质差别

1. **状态分布改成横向条形 + 降序**。原版 `st.bar_chart` 用的是字典序，
   读"谁多谁少"要自己比；现在每行带状态色胶囊、条数、占比，一眼看出主次。
2. **数据库大小改由后端返回**（`database.get_stats()` 新增 `db_size_bytes`）。
   原版在前端 `Path(settings.DB_PATH).stat()` 读文件——React 既拿不到、
   也不该知道 DB 路径，所以这个字段挪到了后端。
3. **极小占比给可见下限**（`MIN_BAR_PERCENT = 1.5`）。1 条 / 1000 条 = 0.1%，
   渲染出来是 0 像素宽的条，用户会以为"这一项没有数据"——而实际上有一条。
   宁可让条形比例稍微失真，也不能让存在的数据看起来不存在。

### 本轮踩到的一个测试陷阱（值得单独记）

`statsUtils.ts` 里那条"非零但极小的占比要有可见下限"的用例，最初断言写的是
`barPercent > 0`。把 `MIN_BAR_PERCENT` 从 `1.5` 改成 `0` 做退化验证时，
**21 项测试全绿**——因为真实占比 0.1 本身就大于 0，断言恒真，等于什么都没测。

判别式必须写成 **`barPercent > percent`**（下限真的把值抬高了）。
改完之后再退化验证，精确报 `expected 0.1 to be greater than 0.1`，这才算测到了。

⇒ 这就是"退化验证要设计**只有正确实现才满足**的断言"这条规则的又一次实证：
**只断言"大于 0"、"非空"、"不为 NaN"这类弱性质，护栏被拆掉也照样绿。**
