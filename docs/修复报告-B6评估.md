## 1. 现状（读函数体确认，不是 grep 结论）

- `agents.py:781 check_relevance(fault_description, evidence)`：独立的一次 LLM 往返，
  返回**三态** `True / False / None`（None = 核验本身没做成）。
- 调用点只有一处：`orchestrator.py:250`，位于 `diagnose_node` 内、
  **在 `agent_diagnose` 之前**、在两条确定性护栏（无依据 / 设备不匹配）之后。

```python
# orchestrator.py diagnose_node 的真实顺序
if "【知识库无相关依据】" in evidence:  → 降级 insufficient_knowledge（不调 LLM）
if not is_equipment_in_evidence(...):  → 降级 insufficient_knowledge（不调 LLM）
relevance = check_relevance(...)       # ← 第 1 次 LLM 往返
  False → 降级 insufficient_knowledge（不调 agent_diagnose）
  None  → llm_failed + 「相关性校验未能完成」
diagnosis = agent_diagnose(...)        # ← 第 2 次 LLM 往返
```

## 3. 方案 A：并进 `DiagnosisOutput`（诊断时顺带声明相关性）

**收益**：每次诊断省 1 次 LLM 往返 ≈ 1~2 s，按 `diagnose` 节点 3293 ms 计，
该节点耗时降约 40%~50%，全流程（不含辩论）约降 8%~10%。

**代价与风险（按严重程度排序）**：

1. **在"不相关"这一支上反而更贵。**
   现在 `relevance is False` 时**不会**调用 `agent_diagnose`，省掉的正是最贵的
   那一次调用。合并后必须先跑完整个诊断才可能说"不相关"——这一支的耗时翻倍。
   只有"相关"的常见分支才省钱。收益与风险是**不对称**的。

2. **判据会被系统性削弱（最要紧的一条）。**
   现在是"先判资料能不能用，再决定要不要诊断"。合并后模型会**先写出根因、
   再自评相关性**——它已经生成过结论，此时再说"资料不相关"等于自我否定。
   LLM 的已知行为是"一旦生成就倾向自洽"，这道防线会从"独立预检"退化成
   "事后自评"，误放行率大概率上升。这正是 `README` 里指标⑦（误降级率）
   的对偶面——**误放行**，而误放行的代价是拿别的设备的资料给出根因。

3. **三态语义会被压平，与硬约束冲突。**
   `MEMORY` 硬约束 4 要求"无依据/不匹配/不相关/模型失败都写明原因"，且
   `check_relevance` 的 `None`（无法判断）必须映射成 `llm_failed` +
   「校验未能完成」。合并后"无法判断"不再是"调用失败"（调用本身成功了），
   只能靠一个额外字段表达。这会引入一种新的状态来源：
   `llm_failed` 从"服务故障"扩展到"模型答了但答不明白"——
   前者该去查服务，后者该换问法，混在一起会把人引向错误的排查方向。

4. **回归面较大**：所有"资料不相关 → 降级"的用例（评估集 + 守卫测试）口径要重跑，
   而这类用例恰好是项目最贵的一类（`TC029/TC030` 那种诚实降级用例）。

## 4. 方案 B：保持现状，只做低风险收窄（**推荐**）

- `check_relevance` 的输入里，`evidence` 是被 `retrieve_evidence` 拼好的完整资料串。
  可以在核验时**只送前 N 条资料**（相关性判断不需要看完所有条目），
  减少它的输入 token —— 不改变任何判定语义，也不需要重跑评估集。
- `workorder`（22.0% token、7617 ms）才是更值得动的对象：它排在耗时第二、
  token 占比与 diagnose 持平，而它的输入是诊断 + 审核 + 成本三份 JSON，
  收窄空间比 `check_relevance` 大得多，且不涉及护栏形态。
- 结论：**在"省一次往返"和"守住跨设备护栏"之间，我建议守护栏。**
